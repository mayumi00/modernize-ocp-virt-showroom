
= Module 02: Service Mesh Integration with Virtual Machines

include::vars.adoc[]

このモジュールでは、*Red Hat OpenShift Service Mesh* を導入し、その追加機能や拡張機能について探ります。これにより、クラウドネイティブな世界において、仮想マシン（VM）をファーストクラスシチズン（主要な構成要素）として扱いながら、その運用や監視の体験をどのように向上させられるかを確認します。

## Objectives（目的）

* OpenShift Service Mesh の導入
* 高度なネットワーキングのための VM と OpenShift Service Mesh の統合
* トラフィック管理ルールの実装、および OSSM を通じた新しい可視化（オブザーバビリティ）機能の確認
* 仮想マシンを使用した高度なセキュリティとテストの構成

[[about-service-mesh]]
== About OpenShift Service Mesh

image::rh1/201-OSSM-ServiceMesh.png[link="self", window=blank, width="100%"]

Red Hat OpenShift Service Mesh は、オープンソースプロジェクトである **Istio**、**Kiali**、**Jaeger** をベースにした統合サービスメッシュソリューションであり、OpenShift 環境におけるマイクロサービス間の通信、セキュリティ、および可視化を簡素化するように設計されています。*トラフィック制御*、*セキュリティポリシー*、および*モニタリング*を含む、サービス間の相互作用を統一された方法で管理できます。

[NOTE]
====
OpenShift https://www.redhat.com/en/topics/microservices/what-is-a-service-mesh[Service Mesh,window=_blank] は、オペレーターを介してインストールできるアドオンサービスです。
====

OpenShift Service Mesh は主にコンテナ化されたワークロード向けに設計されていますが、メッシュ内に統合することで VM もサポートします。VM における主なメリットは以下の通りです。

* *一貫したネットワーキングとセキュリティ* – 相互 TLS（mTLS）暗号化とアクセスポリシーを使用することで、VM はコンテナ化されたワークロードと安全に通信できます。
* *統合された可視化（オブザーバビリティ）* – VM は分散トレーシング（Jaeger）、モニタリング（Prometheus、Grafana）、およびサービストポロジーの視覚化（Kiali）を通じて、通信状態を可視化できます。
* *トラフィック管理* – VM とマイクロサービス間でのインテリジェントなルーティング、負荷分散、およびフェイルオーバーを可能にします。
* *段階的な移行* – レガシーな VM を共存させながら、コンテナ環境へ段階的に移行していくハイブリッドアプローチをサポートします。
* *ポリシーの適用* – VM とコンテナの双方にサービスレベルのアクセス制御とセキュリティポリシーを一律に適用し、コンプライアンスを確保します。

以下のセクションでは、サービスメッシュのアーキテクチャに関する追加情報を提供しています。*時間を節約するために以下のセクションはスキップし*、必要に応じて後でここに戻ってきても構いません。

=== OpenShift Service Mesh Architecture

image::rh1/202-OSSM-Components.png[link="self", window=blank, width="100%"]

プラットフォームの一部として提供される OpenShift Service Mesh は、以下のコンポーネントを通じて、上記のような横断的なアプリケーション機能を追加します。

* *istiod*: メッシュに含まれる VM やコンテナのネットワークにおいて、定義されたすべてのポリシー（暗号化、認可、トラフィック管理、可視化）を適用します。
* *envoy*: VM またはコンテナ型ワークロードのサイドカーコンテナであり、ポリシーを受信して適用することで、VM を効果的にメッシュの一部にします。Envoy は VM と並んで配置され（上の画像を参照）、VM に出入りするすべてのリクエストをインターセプトします。
* *Kiali*: メッシュ内に構成されている内容、含まれるアプリケーションのネットワーク、トラフィックのスループットと遅延、使用されているセキュリティ、構成やネットワークで発生する可能性のある問題、ログ、およびメッシュが提供するその他の多数の機能を UI を通じて視覚化します。
* その他のオブザーバビリティコンポーネント（上の画像を参照）には、より詳細な検査のために `kiali` が視覚化するデータの一部が含まれています。
 `Prometheus` は、メッシュ内の各コンテナ/VM の `envoy` から出力される *メトリクス* を収集します。
 `Grafana` は、運用担当者やビジネスアナリストがパフォーマンス、リクエストのスループット/遅延、成功/失敗などを確認するための追加のダッシュボードを提供します。
* *Gateways*: 1つ以上の `ingress gateway` インスタンスが、外部からサービスメッシュへのトラフィックフローをサポートします。メッシュには VM/コンテナへの直接アクセスを禁止する `network policies` が付属しているため、このゲートウェイが必要になります。また、`egress gateway` はメッシュから外部サービスへの送信トラフィックを制御できます。

[NOTE]
====
お使いのクラスターの管理者がすでに Service Mesh のセットアップを完了していますので、VM でこれらの新しい機能を有効にすることがいかに簡単であるかを見てみましょう。
====

これほど説明してきたにもかかわらず、まだ *Travel Booking* アプリケーションの UI にアクセスできていないことに気づきましたか？

これは、外部にサービスを公開するためのルート（Route）がまだ構成されていないためです。

ユーザーインターフェースにはまだアクセスできないため、まずは内部のサービス間通信を通じてソリューションをテストします。

この演習では、既存のゲートウェイにアタッチし、HTTP リクエストを `control-vm` サービスに転送する `HTTPRoute`（Gateway API）を作成します。右側のターミナルに以下をコピー＆ペーストして、このアクションを実行します。

[,bash,subs="attributes",role=execute]
----
echo "apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: control-vm-httproute
  namespace: {modernize_ocp_virt_username}-travel-control
spec:
  parentRefs:
  - name: gateway-shared
    namespace: istio-gateway
  hostnames:
  - "{modernize_ocp_virt_username}-istio-gateway.{modernize_ocp_virt_apps_domain}"
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /
    backendRefs:
    - name: control-vm
      port: 8080" | oc apply -f -
----

すべてが正しく構成されていれば、`istio-gateway` を介して Travel Control ダッシュボードにアクセスできるようになります。

[[canary-release]]
== Versioning VMs with a Canary Release

サービスメッシュに仮想マシンやコンテナを追加することは、ネットワークの監視やトラフィックフローの視覚化だけが目的ではありません。一部のお客様に新機能を提供したり、一般公開する前にサイトのアップデートをテストしたりするために、アプリケーションの複数のバージョンをデプロイして維持することが求められる場合が多くあります。 +

. このタスクでは、*cars-vm* コンポーネントの新バージョン *v2* をリリースし、新規顧客の *10%* がこの新サービスにアクセスできるようにし、残りの顧客は引き続きバージョン *v1* を使用するように構成します。 +

. すべてが正常に動作することを確認したら、異なる属性でコマンドを再度実行することにより、バージョン *v2* へのトラフィックのルーティングを段階的に *80%* まで引き上げます。 +

. これを実現するために、`cars-vm-v2` という名前で `version=v2` というラベルを持つ新しい VM をデプロイします。 +

. 次に、`cars-vm` サービスの双方のバージョンにトラフィックを振り分けられるように、`DestinationRule` を構成します。 +

. 最後に、定義された比率（パーセンテージ）に従って2つのバージョン間でトラフィックを分割するための `VirtualService` を作成します。 +

. 詳細については、使用されるマニフェスト（ {modernize_ocp_virt_repo}/blob/main/module-02/multipleversions-for-car-vm-in-the-mesh.sh[こちら,window=_blank] ）を参照してください。

右側のターミナルで *{user}-travel-agency* プロジェクトにいることを確認し、上記のすべての構成を配信する以下のスクリプトを実行します。

[,sh,subs="attributes",role=execute]
----
./multipleversions-for-car-vm-in-the-mesh.sh 90 10
----

スクリプトが正常に完了したら、`Virtualization（仮想化） -> VirtualMachines（仮想マシン）` をクリックし、*{user}-travel-agency* プロジェクト内で新しい `cars-vm-v2` が実行されていることを確認します。

image::rh1/216-cars-vm-v2.png[link=self, window=blank, width="100%"]

次に、`Service Mesh -> Istio Config` をクリックします。これにより、`{user}-travel-agency` プロジェクトの下に新しいトラフィック管理構成がリスト表示されます。

image::rh1/217-istio-config-traffic.png[link=self, window=blank, width="100%"]

トラフィック構成を作成して間もなく、トラフィック分割の結果がトラフィックグラフにも反映され始めます。`Service Mesh -> Traffic Graph` をクリックしてそのビューに戻ります。

`cars-vm` が `v1` と `v2` の両方にトラフィックを振り分けていることを確認してください。

image::rh1/218-traffic-graph-v1-v2.png[link=self, window=blank, width="100%"]

右上にある2つのドロップダウンメニューで、グラフの更新周期などを定義できます。

上部のドロップダウンメニューから *Display -> Traffic Distribution* を選択して、サービス間のトラフィック比率を可視化します。

image::rh1/219-traffic-distribution.png[link=self, window=blank, width="100%"]

新しいバージョンが安定していることを確認できたら、バージョン `v2` へのトラフィックルーティングを `80%` に引き上げます。

[,sh,subs="attributes",role=execute]
----
./multipleversions-for-car-vm-in-the-mesh.sh 20 80
----

*Istio 構成* が更新され、間もなくトラフィックグラフにバージョン `v2` へ流れるトラフィックが `80%` であることが表示されます。

image::rh1/220-traffic-distribution-80.png[link=self, window=blank, width="100%"]

[[auth-policies]]
== Access Limitations with Authorization Policies

ネットワークトラフィックの監視やシェーピングの他に、サービスメッシュへの統合によって得られるもう一つのメリットがセキュリティの強化です。

メッシュ内では *トラフィックの暗号化* などのセキュリティ機能がデフォルトで適用されますが、どのサービスに可視性を持たせるか、誰がそれらにアクセスできるかといったアクセスルール（認可ポリシー）はデフォルトでは適用されません。これには次のような二面性があります。

* クラスター内のサードパーティによってデプロイされた不正なサービスが、機密性の高いサービスにアクセスできてしまう可能性がある。
* 非常に大規模なクラスターでは、すべての宛先の組み合わせによって `istio-proxy` サイドカーの構成が非常に肥大化し、ポッドの立ち退き（Eviction）やクラスターの不安定化を引き起こす可能性がある。

これらの潜在的な問題に対処するため、交換される証明書に含まれるプリンシパル（サービス識別情報）に基づいて、`AuthorizationPolicy` リソースと可視性の制限を適用することができます。

[NOTE]
++++
<details>
  <summary style=""><b>About Authorization Policies</b></summary>
  <p style="color:black;">The authorization policy enforces access control to the inbound traffic in the server side Envoy proxy. Each Envoy proxy runs an authorization engine that authorizes requests at runtime. When a request comes to the proxy, the authorization engine evaluates the request context against the current authorization policies, and returns the authorization result, either <b>ALLOW</b> or <b>DENY</b>. Operators specify Istio authorization policies using <b>YAML</b> notation. </</p>
</details>
++++

まず、ベストプラクティスとされる「デフォルト拒否（Default Deny All）」ポリシーを各プロジェクトに適用します。

[,sh,subs="attributes",role=execute]

----
echo "apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: allow-nothing
  namespace: {modernize_ocp_virt_username}-travel-agency
spec:
  {}" | oc apply -f -
----

[,sh,subs="attributes",role=execute]

----
echo "apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: allow-nothing
  namespace: {modernize_ocp_virt_username}-travel-control
spec:
  {}" | oc apply -f -
----

これらのポリシーが適用されたことで、*Travel Booking* アプリケーションのすべてのサービスは通信する権限を失い、相互に通信できなくなります。

`Service Mesh -> Traffic Graph` をクリックして、表示されるようになったすべての通信失敗（エラー）を確認します。

image::rh1/221-traffic-graph-fail.png[link=self, window=blank, width="100%"]

https://{modernize_ocp_virt_username}-istio-gateway.{modernize_ocp_virt_apps_domain}/[Travel Booking Dashboard, window=_blank] にアクセスしてみると、ロードに失敗して *RBAC: access denied（RBAC: アクセスが拒否されました）* というメッセージが返ってくることで、この効果を確認できます。

image::rh1/222-access-denied.png[link=self, window=blank, width="100%"]

次に、2つのきめ細かな `AuthorizationPolicy` リソースを適用して通信を復元します。これにより、以下の間の通信が許可されます。

* `istio-gateway` *->* `control-vm`
* *{user}-travel-portal* 内のサービス *->* *{user}-travel-agency* および *{user}-travel-control* 内のサービス

[,sh,subs="attributes",role=execute]
----
echo "apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: allow-selective-principals-travel-control
  namespace: {modernize_ocp_virt_username}-travel-control
spec:
  action: ALLOW
  rules:
  - from:
    - source:
        principals: [\"cluster.local/ns/istio-gateway/sa/gateway-shared-istio\"]" | oc apply -f -
----

[,sh,subs="attributes",role=execute]
----
echo "apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: allow-selective-principals-travel-agency
  namespace: {modernize_ocp_virt_username}-travel-agency
spec:
  action: ALLOW
  rules:
  - from:
    - source:
        principals: [\"cluster.local/ns/{modernize_ocp_virt_username}-travel-agency/sa/default\",\"cluster.local/ns/{modernize_ocp_virt_username}-travel-portal/sa/default\"]" | oc apply -f -
----

`Service Mesh -> Traffic Graph` に戻ると、*{user}-travel-portal* と *{user}-travel-agency* プロジェクトの間で通信が復元されていることが確認できます。

image::rh1/223-traffic-restored.png[link=self, window=blank, width="100%"]

しばらくすると、 https://{modernize_ocp_virt_username}-istio-gateway.{modernize_ocp_virt_apps_domain}/[Travel Booking Dashboard, window=_blank] へのアクセスも回復するはずです。

image::rh1/224-dashboard-restored.png[link=self, window=blank, width="100%"]

新しいポリシーによって `travel-control` と `travel-agency` サービス間の通信は制限されたままになっていることに気づくかもしれません。これは不要な通信であり、適用された `AuthorizationPolicy` ルールでも許可されていないためです。

ターミナルで以下のコマンドを実行することで、これを確認できます。

[,sh,subs="attributes",role=execute]
----
oc -n {modernize_ocp_virt_username}-travel-control run toolbox --rm -it --image=registry.redhat.io/rhel9/toolbox --restart=Never -- curl -o - -I travels-vm.{modernize_ocp_virt_username}-travel-agency.svc.cluster.local:8000/travels/London
----

この操作が禁止されているという応答（403 Forbidden）を受け取るはずです。

[source,yaml,subs=attributes]
----
HTTP/1.1 403 Forbidden
content-length: 19
content-type: text/plain
date: Mon, 24 Mar 2025 16:10:11 GMT
server: envoy
x-envoy-upstream-service-time: 1
----

== Summary（まとめ）

モジュールの完了、*おめでとうございます！！*

このモジュールでは、*Travel Booking* のネームスペース、コンテナ、および VM をサービスメッシュに導入し、OpenShift Service Mesh が提供するすべての可視化（オブザーバビリティ）ツールを確認しました。これにより、サイドカーコンテナが、VM であるかコンテナであるかを問わず内部のアプリケーションコンポーネントを変更することなく、強化されたセキュリティ、トラフィックシェーピング、ネットワーク監視などの横断的な機能をいかに有効にできるかをご理解いただけたかと思います。

次のシナリオでは、これらの構成の配信を自動化し、要件の変化に応じて、命令的なアプローチではなく *OpenShift GitOps* を使用した宣言的な方法で監視および適用できるようにします。
