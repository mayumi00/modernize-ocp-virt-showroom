
= Module 03: Declarative management and automation of VMs with DevHub and GitOps

include::vars.adoc[]

GitOpsは、宣言的なシステム構成の「唯一の真実のソース（Single Source of Truth）」としてGitを使用する、インフラストラクチャおよびアプリケーション管理へのモダンなアプローチです。

Gitリポジトリを使用してインフラストラクチャを定義・管理することで、GitOpsは自動デプロイ、バージョン管理、および継続的デリバリー（CD）を可能にします。変更はプルリクエスト（Pull Request）を通じて行われるため、一貫性、監査可能性、およびロールバック機能が保証されます。このアプローチにより、チーム間のコラボレーションが向上すると同時に、ヒューマンエラーが削減されます。

さらに、Red Hat Developer Hubのようなツールを活用することで、仮想マシンやその他のアプリケーションワークロードを宣言的な方法で定義し、GitOpsによるデプロイや管理を容易にすることができます。

このモジュールでは、仮想マシンを宣言的に管理する方法、端的に言えば、GitOpsを使用して仮想マシンをよりモダンな方法でデプロイ・管理する方法について簡単に説明します。

[[intro-devhub]]
== Introduction to Red Hat Developer Hub

Red Hat Developer Hub (RHDH) は、ソフトウェア開発プロセスを簡素化・合理化するために設計された、エンタープライズグレードの社内開発者向けポータル（IDP: Internal Developer Portal）です。Red Hat OpenShift Container Platformと組み合わせることで、RHDHはプラットフォームエンジニアリングチームがカスタマイズされたポータルを作成できるようにし、開発者の生産性を向上させ、オンボーディング（環境適応）を加速し、迅速なアプリケーション配信を可能にします。

摩擦や複雑さを軽減することで、RHDHは開発者がエンタープライズクラスのベストプラクティスを遵守しながら、高品質なコードの記述に集中できるようにします。

RHDHは、ソフトウェアテンプレート、事前設計されたソリューション、および動的プラグインを集中管理型のプラットフォームに統合し、統合された環境で運用チームと開発チームの双方に最適なソリューションを提供します。

=== Key features（主な機能）

*Centralized Dashboard（中央管理ダッシュボード）*
開発ツール、CI/CDパイプライン、API、監視ツール、およびドキュメントにアクセスするための単一のインターフェースを提供します。Git、OpenShift、Kubernetes、JIRAなどのシステムと統合されています。

*Dynamic Plugins（動的プラグイン）*
システムを停止することなく、プラグインを動的に追加、更新、または削除できます。Tekton、GitOps、Nexus Repository、JFrog Artifactoryなどの一般的なプラグインがサポートされており、Red Hatによって検証されています。

*Software Templates（ソフトウェアテンプレート）*
リポジトリのセットアップ、変数の挿入、本番パイプラインの作成などのタスクを自動化することで、開発プロセスを簡素化します。

*Role-Based Access Control（RBAC：ロールベースアクセス制御）*
組織のニーズに合わせた詳細なセキュリティ権限でユーザーアクセスを管理します。

*Scalability（拡張性）*
同じツールやサービスへのアクセスを維持しながら、拡大するチームやアプリケーションをサポートします。

*Configuration Management（構成管理）*
集中管理されたリポジトリにより同期されたアップデートが保証され、バージョン管理と環境構成が向上します。

== Introduction to OpenShift GitOps

*Argo CD* をベースにした OpenShift GitOps は、GitOpsの原則をRed Hat OpenShift環境に拡張し、Kubernetesネイティブなアプリケーションや仮想化されたワークロードを管理するための包括的なソリューションを提供します。

Red Hat OpenShift GitOpsは、Gitリポジトリ、継続的インテグレーション/継続的デリバリー（CI/CD）ツール、およびKubernetesを統合したワークフローを提供するオペレーターであり、品質を妥協することなく、より迅速で安全、かつスケーラブルなソフトウェア開発を実現します。

OpenShift GitOpsにより、ユーザーは宣言的なGit駆動のCDワークフローをアプリケーション開発プラットフォームに直接構築し、統合することができます。

開発パイプラインを「DevOps」へと変換する単一のツールというものは存在しません。GitOpsフレームワークを実装することで、アップデートや変更が宣言的なコードを通じてプッシュされ、インフラストラクチャやデプロイ要件、およびCI/CDが自動化されます。

=== Benefits of OpenShift GitOps for virtual machines (VMs)（仮想マシンにおけるOpenShift GitOpsのメリット）

GitOpsは通常、コンテナ化されたアプリケーションに関連付けられますが、OpenShift GitOpsはOpenShift Virtualizationを使用した *仮想マシン（VM）の管理もサポート* しています。これにはいくつかの大きな利点があります。

* *一貫した Infrastructure as Code (IaC)*: VMの構成とライフサイクルをGitで管理することにより、チームはKubernetesアプリケーションに使用されるものと同じ宣言적ワークフローを適用でき、一貫性と再現性を確保できます。
* *自動化されたデプロイとロールバック*: OpenShift GitOpsは、Git内の期待される状態（Desired State）を継続的に監視し、乖離を自動的に調整（リコンサイル）します。これにより、VMが常に正しくデプロイされ、必要に応じて迅速なロールバックが可能になります。
* *セキュリティとコンプライアンスの向上*: Gitベースのワークフローにより、監査可能な変更管理が可能になり、ポリシーやコンプライアンス基準を強制しながら、VM構成に対するすべての変更を追跡およびレビューできます。
* *拡張性とハイブリッドクラウドのサポート*: OpenShift GitOpsは、オンプレミス環境とクラウド環境にまたがるVMのデプロイと管理を容易にし、インフラストラクチャ自動化への統一されたアプローチを提供します。

GitOpsの原則をOpenShift Virtualizationと統合することで、組織はVM管理を合理化し、セキュリティを強化し、ハイブリッドクラウド環境における運用効率を向上させることができます。

== Create an Argo CD application

Argo CDにログインしましたので、`travel-control` コンポーネント用のアプリケーション（App）を作成してみましょう。

Argoコンソールでは、左上の `+ New App` ボタン、または中央の `Create Application` ボタンのいずれかをクリックして、新しいアプリケーションを作成できます。

[[argo-self-heal]]
== Validate Argo CD self-healing

Argo CDによって管理されるアプリケーションを持つことの素晴らしい機能の一つ（このモジュールの前半で行った宣言型VMの手動作成とは異なる点）は、何か問題が発生した際にアプリケーションの健全性を監視できる機能にあります。その後、アプリケーションの定義から再同期を行い、壊れた状態にあるアプリケーションを効果的に回復（ヒーリング）させることができます。

Argo CDの *セルフヒーリング（Self-healing）能力* をテストするために、Argo CDによって管理されているKubernetesリソースを手動で削除してみましょう。*Automated Sync（自動同期）* と *Self-Heal（セルフヒーリング）* を有効にすると、Argo CDはGit内の期待される状態（Desired State）からの乖離（ドリフト）を検出し、*削除されたリソースを自動的に再作成* します。これにより、セルフヒーリングが期待通りに動作していることを確認できます。

=== Enable self-healing（セルフヒーリングの有効化）

まず、travel-control アプリケーションの `Auto-Sync` と `Self-Healing` を有効にする必要があります。

コンソール上部にある *Argo CD* タブに戻ります。

`travel-control` アプリケーションの上部にある `DETAILS` ボタンをクリックします。

image::summit/417-travel-control-details-button.png["travel-control application with DETAILS button highlighted at the top", link=self,window=blank,width=100%]

パネルがスライドして表示され、*Summary（サマリー）* タブが表示されます。*Sync Policy* セクションまで下にスクロールし、`ENABLE AUTO-SYNC` のチェックボックスをクリックします。

image::summit/418-travel-control-autosync-button.png["Sync Policy section with ENABLE AUTO-SYNC button", link=self,window=blank,width=100%]

`Enable Auto-Sync` の新しいウィンドウが表示されたら、`OK` ボタンをクリックします。

image::summit/419-travel-control-autosync-ok.png["Enable Auto-Sync confirmation dialog with OK button", link=self,window=blank,width=100%]

`Auto-Sync` が有効になると、*Sync Policy* セクションが変更され、隣にチェックボックスが付いた `Self Heal` のオプションが表示されます。これを有効にしてください。

image::summit/420-travel-control-sync-policy.png["Sync Policy section showing Auto-Sync enabled with Self Heal Enable button", link=self,window=blank,width=100%]

`Enable Self Heal` の新しいウィンドウが表示されたら、`OK` ボタンをクリックします。

image::summit/421-travel-control-selfheal-ok.png["Enable Self Heal confirmation dialog with OK button", link=self,window=blank,width=100%]

右上隅の `X` をクリックしてパネルを閉じます。

image::summit/422-travel-control-details-close.png["Details panel with the X close button in the upper right corner", link=self,window=blank,width=100%]

=== Test self-healing（セルフヒーリングのテスト）

セルフヒーリング機能をテストするために、*{modernize_ocp_virt_username}-travel-control-new* プロジェクトから *control-vm* を「誤って」削除してみます。

Red Hat OpenShiftコンソールに戻り、左側のナビゲーションメニューで `Virtualization（仮想化） -> VirtualMachines（仮想マシン）` をクリックし、中央の列で *{modernize_ocp_virt_username}-travel-control-new* プロジェクトを選択してから、*control-vm* という名前の仮想マシンをクリックします。

image::summit/423-virt-console-control-vm.png["VirtualMachines page showing control-vm in the travel-control-new project", link=self,window=blank,width=100%]

IMPORTANT: You will need to perform these next few tasks fairly quickly, or the VM may automatically restart due to Argo CD protecting the VM's desired running state.


この画面で、`Stop（停止）` ボタンを使用するか、`Actions（アクション） -> Control（コントロール）` ドロップダウンメニューから `Stop（停止）` のオプションを選択します。

image::summit/424-stop-control-vm.png["control-vm overview with Stop button and Actions dropdown menu", link=self,window=blank,width=100%]

仮想マシンが停止すると、`Actions（アクション）` ドロップダウンメニューでVMを `Delete（削除）` するオプションが利用可能になります。

image::summit/425-delete-control-vm.png["Actions dropdown menu with Delete option for the stopped control-vm", link=self,window=blank,width=100%]

仮想マシンの削除を確認する追加のプロンプトが1つ表示されますので、`Delete（削除）` ボタンをクリックします。

image::summit/426-vm-confirm-delete.png["Confirm VM deletion", link=self,window=blank,width=100%]

削除されたらArgoダッシュボードに戻ると、アプリケーションが `OutOfSync（同期が不一致）` になっているのが確認できます。

image::summit/427-application-unhealthy.png["Argo CD showing travel-control application in OutOfSync and unhealthy state during self-healing", link=self,window=blank,width=100%]

Argo CDダッシュボードは自動化されたプロセスを進み、短時間のうちに以下のような状態遷移を表示します。

. **アプリケーションステータスが「OutOfSync」になる** – 稼働中のクラスターの状態がGitのソースと一致しなくなったことを示します。
. 削除されたリソースが **リソースツリーから一時的に消失** します。
. すぐにArgo CDが **自動同期（Auto-sync）** を行い、削除されたリソースが **再表示** され、期待される状態が復元されます。
. ステータスが **「Synced（同期済み）」および「Healthy（健全）」** に戻り、セルフヒーリングが行われたことが確認されます。

image::summit/428-application-progressing.png["Argo CD progressing through self-healing", link=self,window=blank,width=100%]

すべてのタスクが完了すると、期待通りにすべてのアプリケーションコンポーネントがデプロイされた、以前の健全な状態に戻ります。

image::summit/429-application-healthy.png["Argo CD showing travel-control application restored to Synced and Healthy state after self-healing", link=self,window=blank,width=100%]

OpenShiftコンソールに戻ると、誤って削除した仮想マシンが正常な状態に復元されていることが確認できます。

image::summit/430-vm-running.png["Restored VM running", link=self,window=blank,width=100%]

== Summary（まとめ）

このモジュールでは、Red Hat OpenShift GitOpsについて、そしてアプリケーションやVMを宣言的な方法でデプロイするためにそれがどのように使用できるかを学びました。また、Red Hat Developer Hubについて、そしてVMをホストするために使用されるそれらのGitリポジトリを作成・管理するためにそれがどのように活用できるかを学びました。さらに、アプリケーションや仮想マシンが一度GitOpsによって管理されれば、リソースを既知の良好な期待される状態に復元することで、ユーザーエラーやその他の予期せぬ事態によって影響を受けたアプリケーションをセルフヒーリングできることを実証しました。
