
= Module 03: Declarative Management of VMs with GitOps Automation

include::vars.adoc[]

GitOpsは、宣言的なシステム構成の「唯一の真実のソース（Single Source of Truth）」としてGitを使用する、インフラストラクチャおよびアプリケーション管理へのモダンなアプローチです。

Gitリポジトリを使用してインフラストラクチャを定義・管理することで、GitOpsは自動デプロイ、バージョン管理、および継続的デリバリー（CD）を可能にします。変更はプルリクエスト（Pull Request）を通じて行われるため、一貫性、監査可能性、およびロールバック機能が保証されます。このアプローチにより、チーム間のコラボレーションが向上すると同時に、ヒューマンエラーが削減されます。

[[about-gitops]]
== About OpenShift GitOps

*Argo CD* をベースにした OpenShift GitOps は、GitOpsの原則をRed Hat OpenShift環境に拡張し、Kubernetesネイティブなアプリケーションや仮想化されたワークロードを管理するための包括的なソリューションを提供します。

Red Hat OpenShift GitOpsは、Gitリポジトリ、継続的インテグレーション/継続的デリバリー（CI/CD）ツール、およびKubernetesを統合したワークフローを提供するオペレーターであり、品質を妥協することなく、より迅速で安全、かつスケーラブルなソフトウェア開発を実現します。

OpenShift GitOpsにより、ユーザーは宣言的なGit駆動のCDワークフローをアプリケーション開発プラットフォームに直接構築し、統合することができます。

開発パイプラインを「DevOps」へと変換する単一のツールというものは存在しません。GitOpsフレームワークを実装することで、アップデートや変更が宣言的なコードを通じてプッシュされ、インフラストラクチャやデプロイ要件、およびCI/CDが自動化されます。

=== Benefits of OpenShift GitOps for Virtual Machines (VMs)（仮想マシンにおけるOpenShift GitOpsのメリット）

GitOpsは通常、コンテナ化されたアプリケーションに関連付けられますが、OpenShift GitOpsはOpenShift Virtualizationを使用した *仮想マシン（VM）の管理もサポート* しています。これにはいくつかの大きな利点があります。

* *一貫した Infrastructure as Code (IaC)*: VMの構成とライフサイクルをGitで管理することにより、チームはKubernetesアプリケーションに使用されるものと同じ宣言的ワークフローを適用でき、一貫性と再現性を確保できます。
* *自動化されたデプロイとロールバック*: OpenShift GitOpsは、Git内の期待される状態（Desired State）を継続的に監視し、乖離を自動的に調整（リコンサイル）します。これにより、VMが常に正しくデプロイされ、必要に応じて迅速なロールバックが可能になります。
* *セキュリティとコンプライアンスの向上*: Gitベースのワークフローにより、監査可能な変更管理が可能になり、ポリシーやコンプライアンス基準を強制しながら、VM構成に対するすべての変更を追跡およびレビューできます。
* *拡張性とハイブリッドクラウドのサポート*: OpenShift GitOpsは、オンプレミス環境とクラウド環境にまたがるVMのデプロイと管理を容易にし、インフラストラクチャ自動化への統一されたアプローチを提供します。

GitOpsの原則をOpenShift Virtualizationと統合することで、組織はVM管理を合理化し、セキュリティを強化し、ハイブリッドクラウド環境における運用効率を向上させることができます。

== Create an Argo CD Application

Argo CDにログインしましたので、`travel-control` コンポーネント用のアプリケーション（App）を作成してみましょう。

*Argo CDアプリケーション* とは、Gitリポジトリに基づいてワークロードのデプロイを定義および管理するKubernetesリソースです。アプリケーションの期待される状態をGitからクラスターへと継続的に同期し、一貫性を確保するとともに、乖離が発生した場合には自動ロールバックを可能にします。

Argoコンソールでは、左上の `+ New App` ボタン、または中央の `Create Application` ボタンのいずれかをクリックして、新しいアプリケーションを作成できます。

クリックすると、アプリケーション作成（Create App）ウィザードがスライドして表示されます。

ウィザードには入力が必要なフィールドがいくつかあるため、スクリーンショットに沿って一つずつ手順を進めていきます。

[[argo-self-heal]]
== Validate Argo CD Self-Healing

Argo CDの *セルフヒーリング（Self-healing）能力* をテストするために、Argo CDによって管理されているKubernetesリソースを手動で削除してみましょう。*Automated Sync（自動同期）* と *Self-Heal（セルフヒーリング）* を有効にすると、Argo CDはGit内の期待される状態（Desired State）からの乖離（ドリフト）を検出し、*削除されたリソースを自動的に再作成* します。これにより、セルフヒーリングが期待通りに動作していることを確認できます。

=== Enable Self-Healing（セルフヒーリングの有効化）

まず、travel-control アプリケーションの `Auto-Sync` と `Self-Healing` を有効にする必要があります。

`travel-control` アプリケーションの上部にある `DETAILS` ボタンをクリックします。

image::rh1/417-travel-control-details-button.png[link="self", window=blank, width="100%"]

パネルがスライドして表示されます。*Sync Policy* セクションまで下にスクロールし、`ENABLE AUTO-SYNC` ボタンをクリックします。

image::rh1/418-travel-control-autosync-button.png[link="self", window=blank, width="100%"]

`Enable Auto-Sync` の新しいウィンドウが表示されたら、`OK` ボタンをクリックします。

image::rh1/419-travel-control-autosync-ok.png[link="self", window=blank, width="100%"]

`Auto-Sync` が有効になると、*Sync Policy* セクションが変更され、隣に `Enable` ボタンが付いた `Self Heal` のオプションが表示されます。そのボタンをクリックしてください。

image::rh1/420-travel-control-sync-policy.png[link="self", window=blank, width="100%"]

`Enable Self Heal` の新しいウィンドウが表示されたら、`OK` ボタンをクリックします。

image::rh1/421-travel-control-selfheal-ok.png[link="self", window=blank, width="100%"]

右上隅の `X` をクリックしてパネルを閉じます。

image::rh1/422-travel-control-details-close.png[link="self", window=blank, width="100%"]

=== Test Self-Healing（セルフヒーリングのテスト）

セルフヒーリング機能をテストするために、`{user}-travel-control-new` プロジェクトから *control-vm* を「誤って」削除してみます。

Red Hat OpenShiftコンソールに戻り、左側のナビゲーションメニューで `Virtualization（仮想化） -> VirtualMachines（仮想マシン）` をクリックし、中央の列で `{user}-travel-control-new` プロジェクトを選択してから、*control-vm* という名前の仮想マシンをクリックします。

image::rh1/423-virt-console-control-vm.png[link="self", window=blank, width="100%"]

[IMPORTANT]
====
Argo CDがVMの期待される実行状態を保護するために自動的にVMを再起動してしまう可能性があるため、これ以降のいくつかのタスクはかなり迅速に実行する必要があります。
====

この画面で、`Stop（停止）` ボタンを使用するか、`Actions（アクション）` ドロップダウンメニューから `Stop（停止）` のオプションを選択します。

image::rh1/424-stop-control-vm.png[link="self", window=blank, width="100%"]

仮想マシンが停止すると、`Actions（アクション）` ドロップダウンメニューでVMを `Delete（削除）` するオプションが利用可能になります。

image::rh1/425-delete-control-vm.png[link="self", window=blank, width="100%"]

削除が完了したらArgoダッシュボードに戻ると、すでに復元操作が進行中である可能性が高いです。

Argo CDダッシュボードは自動化されたプロセスを進み、短時間のうちに以下のような状態遷移を表示します。

1. **アプリケーションステータスが「OutOfSync」になる** – 稼働中のクラスターの状態がGitのソースと一致しなくなったことを示します。
2. 削除されたリソースが **リソースツリーから一時的に消失** します。
3. すぐにArgo CDが **自動同期（Auto-sync）** を行い、削除されたリソースが **再表示** され、期待される状態が復元されます。
4. ステータスが **「Synced（同期済み）」および「Healthy（健全）」** に戻り、セルフヒーリングが行われたことが確認されます。

image::rh1/426-application-unhealthy.png[link="self", window=blank, width="100%"]

すべてのタスクが完了すると、期待通りにすべてのアプリケーションコンポーネントがデプロイされた、以前の健全な状態に戻ります。

image::rh1/427-application-healthy.png[link="self", window=blank, width="100%"]

この機会を利用して、 https://{modernize_ocp_virt_username}-ingress-istio-gateway.{modernize_ocp_virt_apps_domain}[Travel Control Dashboard^] がまだ正常に動作しているか検証することもできます。

== Summary（まとめ）

このモジュールでは、Red Hat OpenShift GitOpsについて、およびアプリケーションやVMを宣言的な方法でデプロイするためにそれがどのように使用できるかを学びました。また、一度アプリケーションや仮想マシンがGitOpsによって管理されれば、リソースを既知の良好な期待される状態に復元することで、ユーザーエラーやその他の予期せぬ事態によって影響を受けたアプリケーションをセルフヒーリングできることも実証しました。
